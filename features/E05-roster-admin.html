18.4 F16 — Add paid member to roster

Phase Status Rules Repo refs
1 Parked R-014, R-017 _parked/src/components/league/AddPaidMemberSheet.tsx, RosterPanel.tsx · useAddRosterPlayer

18.4.1 Requirements

As a captain, I add a paid member to my roster before the night starts.

ID Requirement
FR-16.1 "Add paid member" appears on the captain's own roster panel only while the night isn't submitted. Admins always see it
FR-16.2 A drawer searches players (≥ 2 chars): SL, name, member ID, and an "Unpaid" flag
FR-16.3 Unpaid members stay visible but their Add button is disabled, so the refusal makes sense
FR-16.4 POST /teams/{teamId}/roster {playerId}. The server refuses unpaid players with 40003 "That member has not paid dues for this division yet."
FR-16.5 The server refuses a player who already has an active roster (F7 index) with 40001
FR-16.6 On success the drawer closes and the roster refetches

18.4.2 Logic

18.4.3 Edge cases

ID Situation Expected
EC-16.1 Member pays during the night Admin flips is_paid; the captain retries
EC-16.2 Captain adds a player during match 3 Allowed in the MVP (the R-017 "before match 1" rule is Phase 2, F39c)
EC-16.3 Captain tries to poach a player from another team 400; only an admin can transfer

18.4.4 Acceptance criteria

  • AC-16.1 A player-role user doesn't see "Add paid member"; the captain does.
  • AC-16.2 Adding a seeded unpaid player returns 40003 with the copy above.

18.4.5 Implementation gaps (_parked)

  • The button isn't hidden after the night is submitted.

18.6 F18 — Skill-level change and history

Phase Status Rules Repo refs
1 Parked R-050, R-120, R-125 _parked/src/components/league/SkillLevelPanel.tsx, lib/schemas.ts (skillLevelChangeSchema)

18.6.1 Requirements

As an admin, I change a player's skill level with a reason, and anyone with access can see why it changed.

ID Requirement
FR-18.1 Six toggle buttons, SL 2–7 (44 px, aria-pressed). The current level is accent; the pending choice is primary
FR-18.2 Preview: "vs SL 5: races to {now} (was {before})", shown only when the level changed
FR-18.3 Static note: "Applies from the next match. Played matches keep their snapshot."
FR-18.4 Reason is required (trimmed, ≥ 1 char): "Required. Shown in this player's history."
FR-18.5 Save is enabled only if valid and changed. Calls change_skill_level() via POST /players/{id}/skill-level
FR-18.6 History is append-only: "old → new", reason, "by {admin} · {date}". Empty: "No changes yet." With loading and error states
FR-18.7 After saving: invalidate the player list and history; reset the form

18.6.2 Logic

18.6.3 Edge cases

ID Situation Expected
EC-18.1 Player is put up but the opponent isn't yet (no snapshot) The snapshot is taken when both sides are up, so the new SL applies. Acceptable; documented
EC-18.2 Two admins change the same player at once Both succeed in order; history shows both
EC-18.3 9-Ball SL Phase 2 (F32): per-format SL table

18.6.4 Acceptance criteria

  • AC-18.1 Save stays disabled for an empty or whitespace-only reason.
  • AC-18.2 4 → 6 adds a history row "4 → 6" with the reason and the admin's name; played matches still show SL 4.
  • AC-18.3 The preview for SL 6 vs SL 5 reads 5–4.

18.6.5 Implementation gaps (_parked)

  • The preview renders even when the level is unchanged.
  • History has no loading or error state.
