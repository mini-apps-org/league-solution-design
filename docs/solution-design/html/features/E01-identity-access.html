14.4 F1 — Google sign-in

Phase Status Rules Repo refs
1 Built ADR-003, ADR-009 league-be/internal/auth/{handlers,services,services_google,login_transaction}.go · league-fe/src/pages/auth/LoginPage.tsx, src/components/auth/GoogleSignInButton.tsx, src/hooks/useLoginError.ts

14.4.1 Requirements

As a player, I sign in with my Google account so I don't need a league password.

ID Requirement
FR-1.1 The sign-in control is an <a href> to {VITE_API_URL}/api/v1/auth/google/login with no query params. It is never an XHR, because the browser must follow the 302 and show Google's origin in the address bar
FR-1.2 The backend uses Authorization Code + PKCE (S256) + state + nonce, scopes openid email profile
FR-1.3 State, nonce and verifier are sealed with AES-256-GCM in the oauth_tx cookie (10 min, path /api/v1/auth/google), and the cookie is cleared as soon as the callback reads it
FR-1.4 The callback accepts only a verified id_token (signature, iss, aud, exp), a matching nonce, a non-empty sub and email_verified = true
FR-1.5 Users are upserted by google_sub only, never by email
FR-1.6 A new user is redirected to /onboarding; a returning user to /
FR-1.7 Failures redirect to /login?error=cancelled|login_failed|server_error. The FE shows a banner only for these three values
FR-1.8 A signed-in user who opens /login is redirected to /
FR-1.9 After the click the button shows a spinner and is disabled, without preventDefault

14.4.5 Acceptance criteria

  • AC-1.1 Given a new Google account, when sign-in completes, then cookies sid and csrf are set and the browser lands on /onboarding.
  • AC-1.2 Given /login?error=cancelled, then the banner reads "You cancelled the sign-in."
  • AC-1.3 Given a signed-in user, when they open /login, then they are redirected to /.
  • AC-1.4 After sign-in, localStorage contains no token (only locale).

14.5 F2 — Sessions & logout

Phase Status Rules Repo refs
1 Built ADR-003 league-be/internal/auth/{middleware,cleanup,handlers_cookie,repositories}.go · league-fe/src/components/RequireAuth.tsx, src/hooks/useMe.ts

14.5.1 Requirements

ID Requirement
FR-2.1 A session is an opaque 32-byte id (base64url) stored in sessions. There is no JWT and no refresh token
FR-2.2 Absolute lifetime SESSION_TTL (12 h) and idle lifetime SESSION_IDLE_TTL (30 min), both enforced in SQL. Startup fails if idle > absolute
FR-2.3 Every authenticated request updates last_seen_at
FR-2.4 A new session id is issued on every login (prevents session fixation)
FR-2.5 Expired sessions are deleted at startup and then every 24 h
FR-2.6 POST /auth/logout (CSRF required) deletes the session and clears sid and csrf. It returns 204 even with no session
FR-2.7 FE RequireAuth: GET /me with retry: false. Pending → AppSkeleton; error → /login with state.from
FR-2.8 Any 401 outside /me hard-redirects to /login, because there is no refresh
FR-2.9 FE logout clears the React Query cache before navigating to /login

14.5.2 Rules & logic

Cookie (prod) HttpOnly Domain Path Purpose
__Host-sid yes host-only be. / Session
__Secure-csrf no mvip-league.com / Double-submit token, readable by the SPA on www.
__Secure-oauth_tx yes host-only /api/v1/auth/google Login transaction

In development and staging the cookies use plain names (sid, csrf, oauth_tx), without Secure and without Domain.

14.5.3 Edge cases

ID Situation Expected
EC-2.1 Captain idles for 35 min mid-night, then taps save 401 40102 → /login; unsaved form input is lost. Recommendation: show a "session expired" toast first
EC-2.2 The night runs longer than 12 h Re-login is required. Acceptable, since nights are about 4 h
EC-2.3 Logout without a cookie 204, nothing deleted
EC-2.4 Two tabs open; one logs out The other gets a 401 on its next request → /login

14.5.4 Acceptance criteria

  • AC-2.1 Given a session idle for 31 minutes, when /me is called, then the response is 401 with code 40102 and the sid cookie is cleared.
  • AC-2.2 When the user logs out, then POST /auth/logout sends X-CSRF-Token, returns 204 and the app shows /login.

14.5.5 Implementation gaps

  • DeleteUserSessions ("log out everywhere") exists in the repository layer but no route uses it.
  • No FE warning before idle expiry. Consider a 25-minute warning on scoring screens.

14.7 F4 — `/me` with role and playerId

Phase Status Rules Repo refs
1 Built basic · Missingrole, playerId ADR-006 league-be/internal/auth/handlers.go (Me) · league-fe/src/types/auth.ts (roleOf, needsMemberLink), src/hooks/useRole.ts

14.7.1 Requirements

ID Requirement
FR-4.1 GET /me returns {user: {id, email, name, avatarUrl, role, playerId}}
FR-4.2 role comes from users_roles, taking the highest by ADMIN > CAPTAIN > PLAYER. A user with no row is PLAYER
FR-4.3 playerId is the players.id where players.user_id = users.id, or null
FR-4.4 The FE treats only playerId === null as "needs link". undefined (an older backend) leaves the gate inactive

14.7.2 Logic

sql
SELECT r.code
FROM users_roles ur
JOIN roles r ON r.id = ur.role_id
WHERE ur.user_id = $1
ORDER BY CASE r.code WHEN 'ADMIN' THEN 1 WHEN 'CAPTAIN' THEN 2 ELSE 3 END
LIMIT 1;  -- no row → 'PLAYER'

14.7.3 Edge cases

ID Situation Expected
EC-4.1 User has both ADMIN and CAPTAIN role = ADMIN. Captain-owns-night still applies through players.user_id
EC-4.2 User has the CAPTAIN role but isn't captain_player_id of any team role = CAPTAIN, but viewerCanManage is false on every night
EC-4.3 Linked player is deleted user_id FK is ON DELETE SET NULL → playerId becomes null → onboarding again

14.7.4 Acceptance criteria

  • AC-4.1 Given the seeded captain@example.test, /me returns role: "CAPTAIN" and the playerId of member 95007620.
  • AC-4.2 Given a user with no users_roles row, role is "PLAYER".

14.8 F5 — Onboarding: link member ID

Phase Status Rules Repo refs
1 Built UI · Missing API Q31, Q33 league-fe/src/pages/OnboardingPage.tsx, src/components/auth/MemberPreviewCard.tsx, src/lib/member-id.ts, src/hooks/useMemberLink.ts, src/queries/members.ts

14.8.1 Requirements

As a newly signed-in player, I enter the member ID on my league card so the app knows which player I am.

ID Requirement
FR-5.1 Shows "Find your member ID" and "Signed in as {email}", plus a numeric input (inputMode=numeric, max 8) with a real label
FR-5.2 Input is normalized to digits only and truncated to 8 (normalizeMemberId)
FR-5.3 Lookup runs once the ID has 8 digits, or on blur when it has at least 4. Never on every keystroke
FR-5.4 The preview shows the minimum: displayName, SL, team number and name, a captain flag, alreadyLinked, linkedToMe
FR-5.5 Confirm is enabled only when a preview exists and the member isn't taken by another account (isTaken = alreadyLinked && !linkedToMe). Re-linking to yourself is allowed (idempotent)
FR-5.6 Linking waits for the /me refetch before navigating to /, so the gate never sees a stale playerId: null
FR-5.7 "Not you? Sign out" logs out
FR-5.8 The backend refuses linking to a member owned by another user (40006) and linking a user who already has a different member (40007). An unknown ID returns 40005

14.8.2 Logic

ID Situation Expected
EC-5.1 User types 9500-7620 Normalized to 95007620
EC-5.2 Two people race to link the same member The first wins; the second gets 40006
EC-5.3 Double-tap on confirm The second call is idempotent (linkedToMe), no error
EC-5.4 Attacker enumerates IDs via preview Rate-limit the endpoint and reveal only a display name (Q31)
EC-5.5 Member not on any team Card shows "No team yet"

14.8.5 Acceptance criteria

  • AC-5.1 Given 00000000, the alert reads the 40005 copy and receives focus.
  • AC-5.2 Given a member linked to another account, the card shows the warning tint and confirm is disabled.
  • AC-5.3 After linking, /me.playerId is set and the user never sees /onboarding again.

14.8.6 Implementation gaps

  • The backend endpoints don't exist, so every real user is stuck on onboarding. This is the most urgent part of E01.
  • The 8-digit length is an FE assumption (MEMBER_ID_LENGTH); the DB has no length rule.

14.9.1 Requirements

ID Requirement
FR-6.1 Every league write route is wrapped in RequireAuth plus a role check
FR-6.2 Captain-owns-night: put-up, result and submit are allowed when the role is ADMIN, or when the role is CAPTAIN and the user's player is captain_player_id of the night's home or away team

Permission codes (seeded): player.read, match.put_up, match.enter_score, match.submit, roster.manage, player.change_skill_level, season.manage. In the MVP, checks are by role and ownership; permission codes become checks when the LO and Rep roles arrive (F50).
