20.2 Phase 2 deep dive

20.2.1 The model in one sentence

Every tap is an immutable event. A pure reducer, the same in TypeScript and Go and tested with shared JSON fixtures, folds events into the live state. The server owns ordering (seq), stores events in Postgres, and fans state out through Redis.

20.3 F26 — Coin flip & lag

Phase Status Rules Repo refs
2 Target R-030, R-031, R-100 · 08 §2–§3 Phase 1 analogue: firstPutUpFor(order) in _parked/src/lib/night.ts (odd → home)

20.3.1 Requirements

As a scorekeeper, I record who won the coin flip (that decides who puts up first) and, for each match, who won the lag (that decides who breaks and how innings are counted).

ID Requirement
FR-26.1 Before match 1, the night records a coin flip: `{winnerTeamId, choice: "put_up_first"
FR-26.2 The coin flip replaces the Phase 1 fixed rule (odd orders home). After it, put-up order alternates: the starting team puts up in orders 1, 3, 5 and the other team in 2, 4 (R-030/R-031)
FR-26.3 After both players of a slot are up, the match enters Lag: the scorer taps the lag winner, then the lag winner's choice of breaker (usually themselves)
FR-26.4 LAG_RECORDED {winnerPlayerId, breakerPlayerId} sets breaker, activePlayer = breaker, and secondShooter = lag loser (innings increment when the lag loser's turn ends, R-100)
FR-26.5 Rack-to-rack break rule per division bylaw: winner_breaks (APA 8-Ball default) or alternate
FR-26.6 The scorekeeper's name is recorded per individual match (R-105), prefilled with the device user's name
FR-26.7 Undo is allowed for the lag until the first shot event of rack 1

20.3.2 Logic

Coin flip → put-up order

Lag → breaker and innings side

text
on LAG_RECORDED(winner, breaker):
  assert status == LAG and breaker in {home, away}
  lagWinner     = side(winner)
  secondShooter = other(lagWinner)            # R-100, innings side
  rack          = { no: 1, breaker: side(breaker), firstTurnLive: true,
                    timeoutsLeft: timeouts(SL) }  # R-104
  activePlayer  = side(breaker)
  status        = IN_PROGRESS

20.3.6 Edge cases

ID Situation Expected
EC-26.1 Coin flip skipped (old client or Phase 1 fallback) Default to Phase 1 alternation (odd → home)
EC-26.2 Lag winner chooses the opponent to break Allowed: breaker = other(lagWinner); secondShooter stays the lag loser
EC-26.3 Wrong lag winner tapped Undo before the first shot; after that, an admin correction only

20.3.7 Acceptance criteria

  • AC-26.1 Given away wins the toss and chooses to put up first, then the put-up order is away in 1, 3, 5 and home in 2, 4.
  • AC-26.2 Given home wins the lag, when the away player's turn ends, then innings = 1, and when the home player's turn ends first, innings stays 0.
  • AC-26.3 Given a recorded lag and no shot yet, when Undo is tapped, then the slot returns to LAG.

20.4 F27 — Live 8-Ball scoring

Phase Status Rules Repo refs
2 Target R-060–R-062, R-100–R-106, R-050 · 08 §4.1 Phase 1 analogue: pointsFor() in _parked/src/lib/rules.ts

20.4.1 Requirements

As a scorekeeper, I tap through each turn of an 8-Ball match on one screen, and the app tracks games, innings, defensive shots and time-outs exactly as the paper scoresheet would.

ID Requirement
FR-27.1 The live screen shows both players (name, SL, games won / needed, DS count, time-outs left), the active player highlighted, rack number, match innings and a shot timer (informational, R-106)
FR-27.2 Actions for the active player: Turn Over, Defensive Shot, Time-out, End Rack…
FR-27.3 TURN_OVER(p): p must be active. Sets firstTurnLive = false. If p == secondShooter, then innings++. Switches the active player (R-100, R-101)
FR-27.4 DEFENSIVE_SHOT(p): ds[p]++, then the same effect as Turn Over (R-102)
FR-27.5 TIMEOUT(p): only if timeoutsLeft[p] > 0; resets every rack. SL ≤ 3 → 2, SL ≥ 4 → 1 (R-104, configurable)
FR-27.6 The match completes when a player reaches their race. Points use the same points8 as Phase 1: 3/0 shutout, 2/1 hill-hill (loser = race − 1), otherwise 2/0
FR-27.7 Undo reverts only the last non-undone event of the match (UNDO {revertsSeq}); the projection is re-reduced. Undo after the match-ending rack re-opens the match and clears its points
FR-27.8 Switch active player in the ⋮ menu corrects a wrong state without undoing (R-062)
FR-27.9 Races come from the SL snapshot taken at put-up (R-125). An SL change mid-night affects later slots only (R-050)

20.4.2 Logic: turn reducer

Match completion (shared with Phase 1)

text
on rack won by w:
  won[w] += 1
  if won[w] == needed[w]:
     l = other(w)
     pts = won[l] == 0             ? (3,0)
         : won[l] == needed[l] - 1 ? (2,1)     # hill wins over standard (needed 2, won 1)
         :                           (2,0)
     status = COMPLETED

20.5.1 Requirements

As a scorekeeper, I end a rack with the exact outcome. As a player, my break-and-runs and golden breaks are counted on my profile.

FR-28.6 The match breakdown (R-144) lists racks: number, breaker, winner, outcome code, innings

20.6 F29 — Offline scoring sync

Phase Status Rules Repo refs
2 Target NFR-04 · 08 §5 new league-fe/src/lib/scoring/{queue,sync}.ts

20.6.1 Requirements

As a scorekeeper in a basement pool hall with bad signal, I keep scoring without waiting. Nothing I tap is lost or counted twice when the connection comes back.

ID Requirement
FR-29.1 Every event gets a client idempotencyKey (UUIDv7) and the expectedSeq the client believed was current
FR-29.2 Events are applied to the local state at once (TS reducer) and written to an IndexedDB queue before any network call
FR-29.3 A sync loop sends up to 50 queued events per request, in order. It runs on enqueue, on online, on visibility change, and every 5 s while the queue isn't empty
FR-29.4 Server: duplicate idempotencyKey → 200 with the original seq (no-op). Events are processed in order in one transaction; the first invalid event stops the batch and is reported
FR-29.5 409 stale → the client fetches events?after=<serverSeq>, applies them, re-applies its still-pending events on top (rebase), and retries. Pending events that become invalid after the rebase are dropped with a visible notice
FR-29.6 The UI shows sync status: ✓ synced · ↻ syncing n · Assumption offline n pending. Submitting the night (F15) needs an empty queue
FR-29.7 The queue survives reloads and app restarts. It's keyed by team match and cleared after submit
FR-29.8 The service worker still never caches /api/v1 (F20). Offline support lives in app code, not in SW caching

20.6.5 Edge cases

ID Situation Expected
EC-29.1 The same batch is sent twice (timeout, then retry) The second is an idempotent no-op (08 §8 #9)
EC-29.2 Two devices write at the same seq The one without the lease is rejected (F30); otherwise, 409 and rebase
EC-29.3 Phone storage full Show a blocking error; offer "Enter final score instead"
EC-29.4 App killed mid-sync Events not acked stay queued; resent on next open
EC-29.5 Offline for the whole night Scoring works; submit waits for sync with a clear "Connect to submit" state

20.6.6 Acceptance criteria

  • AC-29.1 Given airplane mode for 20 events, when the network returns, then the server holds exactly those 20 events in order.
  • AC-29.2 Given a 409, then after rebase the client state equals the server state plus the pending events.
  • AC-29.3 Given a non-empty queue, then "Submit night" is disabled with the pending count.

20.6.7 Open questions

20.7 F30 — Scoring lease & live viewers

Phase Status Rules Repo refs
2 Target NFR-11 · 08 §1.5, §5 —

20.7.1 Requirements

As a captain, only one phone scores each match, so there are no double taps from two devices. If that phone dies, I can take over. Teammates and friends watch the score live.

ID Requirement
FR-30.1 A lease per individual match: Redis SET lease:individual:{id} {deviceId, userId} NX EX 60, refreshed by every write and by a heartbeat every 20 s
FR-30.2 Only the lease holder can send rack events. Others get 40930 lease held by {name} and see the match read-only
FR-30.3 Take over: a captain of either team or an admin can take the lease with a confirm dialog. The previous holder is told "Scoring moved to {name}" and becomes read-only. It's audited (F41)
FR-30.4 A lease expires after 60 s without a heartbeat; the next eligible device acquires it automatically
FR-30.5 Live viewers: GET /ws/team-matches/{id} (cookie-authenticated; any signed-in user in Phase 2, public later) receives the full state on connect and a new state on each committed event
FR-30.6 Fan-out: API pods SUBSCRIBE match:{teamMatchId} in Redis and push to their local sockets. p95 from commit to viewer < 1 s (NFR-11)
FR-30.7 Fallback: if a WebSocket can't connect, poll GET /team-matches/{id}/live every 5 s
FR-30.8 Connection limits: 200 viewers per team match, idle timeout 30 min, ping every 25 s

20.7.5 Edge cases

ID Situation Expected
EC-30.1 Redis restarts Leases vanish; the next write re-acquires. Viewers reconnect and get state from Postgres
EC-30.2 Pod with many sockets is drained Clients reconnect to another pod (jittered backoff)
EC-30.3 Two take-overs at once The last write wins in Redis; both actions are audited, and the loser sees read-only
EC-30.4 A viewer's network is slow The server drops intermediate states and always sends the latest

20.7.6 Acceptance criteria

  • AC-30.1 Given phone A holds the lease, when phone B sends an event, then it's rejected with 40930 and B shows read-only.
  • AC-30.2 Given 20 viewers on a match, when an event commits, then all 20 receive it within 1 s at p95 (k6 WS check, F46).
  • AC-30.3 Given a take-over, then audit_log has a row with the old holder, the new holder and the time.
